# Carry reylo's lessons into the statement layer and SurrealKit rollouts

[reylo](https://github.com/reylosql/reylo) types `.sql` files for TypeScript with no generated files. It was read at commit `ba71851c` (MIT) for what this package and SurrealKit can learn from it. This goal holds every lesson worth taking, as thirteen lanes. It is a living execution file: keep it true while the work runs, and delete it in the change that closes the last lane.

## Terminal outcome

**Outcome.** An authored `.surql` statement is checked against the schema and a real engine when its module is generated, takes its parameter and result types from the generated descriptors wherever its text proves them, and can be imported without generated files. A write reports a duplicate on a unique index, or a record that already exists, as a typed error that names the index. `surrealkit rollout plan` proposes a backfill when a field is renamed. Each of the thirteen lanes below is closed by its own checks.

**Who receives it.** Developers and coding agents who write SurrealQL against a SurrealKit schema. Today a misspelt projected field, an invalid statement and a wrong result codec all surface when the statement runs. After this goal the first two fail the build, and the third cannot happen for the statements whose types are derived.

**What would disprove it.** Any of three findings. SurrealDB 3.3 reports a unique-index violation in a form from which the index name cannot be read with certainty, which narrows lane L03 to record-exists errors and to 4.0. TypeScript 7.1 is released without content mappers, or with a protocol that no longer accepts TypeScript text for a mapped file, which closes lane L07. The single-table pattern of lane L04 matches none of the authored fixtures under `test/fixtures/statements*`, which would mean the derived types serve no real statement.

This does not mean:

- A SurrealQL parser in TypeScript. The analyzer stays a lexer that records nothing where it is not certain.
- Types for every authored statement. A text outside the recognised patterns stays a `part` with the codecs its author declares, generated byte for byte as it is today.
- A database or an engine as a requirement for generating modules. The engine check is a flag, and `effect-surrealkit statements` without it behaves as it does today.
- The end of the `statements` command. The content mapper is a second supported way to get the same modules, and both render through one function.
- A lane built because reylo has it. Every lane passes the admission gate below first, and a lane that fails it is closed, which is a complete result.
- Done when the types compile. A lane that touches what an engine does is closed by an engine test on SurrealDB 3.3 and 4.0, asserting each side where they differ.
- Any change to existing generated output, except the doc comments of lane L08.

### L03. Typed constraint errors

Measure first: record the kind, details and message of each case below on SurrealDB 3.3, next to the 4.0.1 rows above, and pin both in `test/conformance.test.ts`.

- `StatementRecordExists` is raised from the structured `AlreadyExists` error of kind `Record`.
- `StatementIndexConflict<Index>` is raised when the engine's message names a unique index the statement declares. Its `index` is typed as the union of those names.
- A write builder (`create`, `insert`, `insertRelation`, `update`, `upsert`, `relate`) over a descriptor declares that table's unique indexes, taken from `indexes`. A table with no unique index adds no `StatementIndexConflict` to the statement's error type. What `onDuplicate` and `INSERT IGNORE` declare follows what an engine test shows they can raise.
- `make` and `sequence(...).define` accept a declared list of index names for authored text.
- An index the statement does not declare, and a message that does not match the pinned pattern, stay `StatementRequestError`, as today.
- In a `transaction`, the error names the statement that declares the index, as `StatementThrown` does.
- Conformance tests cover a duplicate through `CREATE`, `INSERT`, `UPDATE`, `UPSERT` and `RELATE`, and an existing record through `CREATE` and `INSERT`, on both engine lanes.
- A type test shows `Effect.catchTag('StatementIndexConflict', (e) => e.index)` narrowed to the literal union.
- A test asserts that the message, `String(error)` and the JSON form of each new error contain no data value: neither the duplicated value nor a record key.
- The README's error table gains both rows, and the diagnostic snapshot is refreshed.

Admission note, 2026-11-23, at `a67c749`:

1. **What is worse today?** Yes. A `create` over `person` that duplicates `uniq_email`, and a `CREATE` of an id that exists, each fail as `StatementRequestError` with the message `SurrealDB request failed` on both engines, so a caller cannot tell a taken value or id from a transport failure without reading the raw `cause`, which the package keeps private. After the lane the same two requests fail as `StatementIndexConflict` (`index: "uniq_email"`) and `StatementRecordExists` on both (`l03-before-after.txt` in the same evidence).
2. **Is this the better way?** Yes, for a write that expects the value to be free. Alternatives considered: SurrealDB's `UPSERT`, `INSERT IGNORE` and `ON DUPLICATE KEY UPDATE` handle a value that may be taken without an error, and the README points at them first; they do not help a write whose collision is a domain error (an email already registered), which today has no typed outcome. A `SELECT` before the write races with a concurrent write, and the unique index is the authority. Reading `cause` in each caller repeats the classification everywhere and exposes the raw message. The record-exists case uses the engine's structured error, so no message is read. The duplicate case has no structured form on either version, so it reads the message under resolved decision 8, and lane L13 asks SurrealDB for a structured one.
3. **With SurrealDB or against it?** With it, narrowed to what the engine states with certainty. Documentation read on 2026-11-23, every page marked `surrealdb_version: "4.x"` (none is published for 3.x; the 3.3.4 behaviour is the conformance rows):
   - <https://surrealdb.com/docs/reference/protocols/errors>: a duplicate record is `{ "kind": "AlreadyExists", "details": { "kind": "Record", … } }`; the message "is free to change between releases, so treat it as text to display rather than something to match on". This is the risk the lane takes for unique indexes, held by decision 8: the message is read only in the form pinned on both versions and only for a declared name, so a changed message fails the conformance rows and falls back to `StatementRequestError`, never to a wrong class.
   - <https://surrealdb.com/docs/surrealql/statements/define/indexes> and <https://surrealdb.com/docs/surrealql/statements/upsert> show the unique-index error in the measured form (``Database index `userEmailIndex` already contains 'test@surrealdb.com', with record `user:1` ``).

Not part of this lane: a typed `INSERT IGNORE` builder. Authored text writes `INSERT IGNORE` today; a builder for it is a possible later lane.

Narrowed: the index name is read with certainty on 3.3 and 4.0, so the lane is not narrowed to 4.0. ### L05. `statements --verify`

- A flag takes the schema as SurrealQL files, in the order they apply. It needs the optional peer `@surrealdb/node`; when the peer is missing the command fails with the install command.
- The command starts an in-process, in-memory engine, loads the schema, and sends each complete text once with no bindings.
- A parse error is a problem with the file, line and column the engine reports. A result count that differs from `slots` is a problem. Other errors a text meets with no bindings are not problems.
- It combines with `--check`, and writes nothing in that mode.
- The same check is exported as a function for a build that generates in process.
- `effect-surrealkit/analyze` stays host-neutral: a test asserts that its built module does not import `@surrealdb/node`.

### L10. A proven result key and total order

- A statement can carry two facts: `key`, the fields that identify a result row, and `ordered`, that its rows come in a total order.
- `select` sets `ordered` only when its `ORDER BY` ends with `id` or covers every column of one unique index, and sets `key` only when `id`, or every column of a unique index with no optional column, is projected. In every other case the fact is absent.
- `make` and `sequence(...).define` accept both as declarations.
- Type tests and unit tests cover each rule and its refusals. An engine test shows that an `ordered` statement returns rows with equal sort values in the same order on repeated runs.

### L07. `.surql` imports through a content mapper

### L11. Rename proposals in `rollout plan`

- When a plan removes one field and adds one field on the same table whose definitions are identical apart from the name, `plan` records the pair in the manifest's `renames` and adds an expand-phase `run_sql` step that copies the old field's values into the new one, marked unconfirmed.
- `rollout lint` and `rollout start` refuse a manifest with an unconfirmed step, as they refuse a `revert_migration` step with an empty `using`. The author confirms the step or deletes it.
- The removal of the old field stays in the contract phase.
- When several removed and added fields could pair in more than one way, `plan` proposes nothing and lists the candidates in a warning.
- A manifest with no renames serialises exactly as before, so the checksum of every existing manifest is unchanged. A snapshot test proves it.
- Tests cover a detected rename, definitions that differ, the ambiguous case, and rows that keep their values through `rollout up` and `rollout up --complete` on the embedded engine.
- The `rollout_plan` MCP tool reports the proposal. The root README's "Migrating existing records" section describes it.

Admission note, 2026-11-23, at `674c57b`:

1. **What is worse today?** Yes. `rollout plan` refuses every field removal and addition on one table (`validate_autoplan`, ``cannot tell apart from a rename``), even when the two definitions are the same apart from the name, so every rename needs a manifest written by hand, backfill and all. The first test of the lane plans `person.email` to `person.mail` and fails on that refusal at this revision.
2. **Is this the better way?** Yes, narrowed. SurrealDB has no native rename or copy, so an `UPDATE` in the expand phase is SurrealDB's own way, not an emulation. Alternatives checked:
   - `ALTER FIELD … RENAME TO`, `ALTER TABLE … RENAME TO`, `ALTER FIELD … NAME` and `RENAME FIELD` are parse errors on the embedded engine (surrealdb-core 4.0.0, the crate's engine). The 4.x `ALTER` pages list no rename clause for a field or a table. The only rename they document is `ALTER TYPE`, which renames the values of a union type.
   - `MIGRATE EXISTING ROWS … USING` reads only `$value`. The `DEFINE FIELD` page says so, and the engine refuses `$this.email`, `$parent.email` and a bare `email` with ``the transform reads only `$value` ``, through `DEFINE FIELD` and through `ALTER FIELD` alike. `ALTER TABLE … MIGRATE EXISTING ROWS` only removes undeclared fields.
   - A `VALUE` clause that reads the old field applies only on a write ("Defining a field does not change the records already in the table"). `COMPUTED` stores nothing, and `GRAPHQL_ALIAS` renames only the GraphQL name. None of these moves stored values.
   - SurrealDB University adds a field with `DEFINE FIELD` and then fills it with `UPDATE`.
   - The proposal is unconfirmed, so nothing that plan inferred runs until the author has read it, as with a `revert_migration` step.
3. **With SurrealDB or against it?** With it, for the narrowed part. The copy is an `UPDATE` in the expand phase, and the removal stays in the contract phase, which matters because at level 4 `REMOVE FIELD` clears the values. Measured on the embedded engine, at compatibility level 4:
   - `UPDATE person SET mail = email WHERE email != NONE` copies every value, leaves a row with no value untouched, copies a `NULL` as `NULL`, and fills a new `UNIQUE` index.
   - Adding a `TYPE string` field to a populated `SCHEMAFULL` table is refused without `MIGRATE EXISTING ROWS`. The catalog hash leaves that clause out, so a new field that carries it still pairs.
   - `READONLY` on the new field makes the copy fail with ``Found changed value for field `b` … but field is readonly``, so such a pair is not proposed.
   - The `UPDATE` evaluates `VALUE` clauses again on every row it touches. A `VALUE time::now()` field took a new value, so a pair with `VALUE` is not proposed, and `COMPUTED` holds nothing to copy.
   - `UPDATE` events fire for each row. That is documented, not refused.

   Not applicable to 3.3: the crate needs SurrealDB 4.0 or later (root README, "Migrating existing records").

   Documentation read on 2026-11-23, every page marked `surrealdb_version: "4.x"`: <https://surrealdb.com/docs/surrealql/statements/alter>, <https://surrealdb.com/docs/reference/query-language/statements/alter/field>, <https://surrealdb.com/docs/reference/query-language/statements/alter/table>, <https://surrealdb.com/docs/surrealql/statements/define/field> and <https://surrealdb.com/learn/fundamentals/schemafull/schemafull-crud#updating-fields-and-tables>. The engine output is saved as `l11-engine-probe.txt` in the topic evidence of `20261123-decide-and-build-reylo-inspired-improvements`.

Narrowed to: a pair is a removed field and an added field on the same table whose names are each one identifier, with no `.` or `[`. Their statements must hash the same once the added field's name is written as the removed one's, which compares the catalog's own hashes and needs no old SQL. The definition must not carry `READONLY`, `VALUE` or `COMPUTED`. Nested fields, indexes and other kinds are out of scope and are still refused as today.
