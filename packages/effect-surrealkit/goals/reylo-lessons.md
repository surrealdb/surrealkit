# Carry reylo's lessons into the statement layer and SurrealKit rollouts

[reylo](https://github.com/reylosql/reylo) types `.sql` files for TypeScript with no generated files. It was read at commit `ba71851c` (MIT) for what this package and SurrealKit can learn from it. This goal holds every lesson worth taking, as thirteen lanes. It is a living execution file: keep it true while the work runs, and delete it in the change that closes the last lane.

## Terminal outcome

**Outcome.** An authored `.surql` statement is checked against the schema and a real engine when its module is generated, takes its parameter and result types from the generated descriptors wherever its text proves them, and can be imported without generated files. A write reports a duplicate on a unique index, or a record that already exists, as a typed error that names the index. `surrealkit rollout plan` proposes a backfill when a field is renamed. Each of the thirteen lanes below is closed by its own checks.

**Who receives it.** Developers and coding agents who write SurrealQL against a SurrealKit schema. Today a misspelt projected field, an invalid statement and a wrong result codec all surface when the statement runs. After this goal the first two fail the build, and the third cannot happen for the statements whose types are derived.

**What would disprove it.** Any of three findings. SurrealDB 3.3 reports a unique-index violation in a form from which the index name cannot be read with certainty, which narrows lane L03 to record-exists errors and to 4.0. TypeScript 7.1 is released without content mappers, or with a protocol that no longer accepts TypeScript text for a mapped file, which closes lane L07. The single-table pattern of lane L04 matches none of the authored fixtures under `test/fixtures/statements*`, which would mean the derived types serve no real statement.

This does not mean:

- A SurrealQL parser in TypeScript. The analyzer stays a lexer that records nothing where it is not certain.
- Types for every authored statement. A text outside the recognised patterns stays a `part` with the codecs its author declares, generated byte for byte as it is today.
- A database or an engine as a requirement for generating modules. The engine check is a flag, and `effect-surrealkit statements` without it behaves as it does today.
- A stable content mapper. It is experimental until TypeScript 7.1 is released, and the `statements` command stays the supported path.
- Done when the types compile. A lane that touches what an engine does is closed by an engine test on SurrealDB 3.3 and 4.0, asserting each side where they differ.
- Any change to existing generated output, except the doc comments of lane L08.

## Resolved decisions

Ruled by Ben Snyder on 2026-11-23:

1. Every item in this file is in this one goal, and its work lands on `feat/effect-surrealkit-statements`, the branch of PR 125. This replaces the PR description's statement that only fixes go onto the branch from here.

Carried from the package's existing rules, which each lane keeps:

2. Refuse rather than guess. A new inference records nothing when it is not certain, as the analyzer does now (README, "Statements from `.surql` files").
3. The text of a statement never depends on an input value. No lane adds a way to put one there.
4. Error messages, default inspection and JSON output never show raw server diagnostics or data values. A new error class carries schema names (an index, a table) in its message and keeps everything else behind `cause` (README, "Running statements").
5. Generated output is deterministic, written atomically, and checked by `--check`. Every path that renders a part module calls the one renderer, `renderStatementModules`.
6. A message pattern is used to classify an engine error only when a conformance test pins that message on both engine lanes. A message that does not match keeps today's `StatementRequestError`.

### L01. Check every authored fixture against an engine

Extend `test/analyze-engine.test.ts` from one generated part to every `.surql` file under `test/fixtures/statements`, `statements-binds` and `statements-presence`.

- For each complete text the engine accepts the text without a parse error and returns exactly the number of results the analyzer derived as `slots`.
- The test reads the directories, so a new fixture is covered without editing the test.
- A fragment, a template or any other file that cannot be sent as it stands is named in the test with its reason. The test fails when a named file no longer exists.
- One test changes a derived `slots` by one and asserts that the comparison fails, so the check is shown to be able to fail.
- It runs on the embedded engine and on `SURREAL_BIN`.

### L02. Pin the skipped tests of each lane

- A committed list per lane (embedded, `SURREAL_BIN` on 3.3, `SURREAL_URL`) names every skipped test in full.
- One command runs the suite for a lane and exits 1 when the skipped tests differ from the list in either direction, printing the differences. An environment variable rewrites the list.
- The package's CI workflow runs the command on the lanes it already runs.
- The README's Development section says how to run and update it.

### L03. Typed constraint errors

Measure first: record the kind, details and message of each case below on SurrealDB 3.3, next to the 4.0.1 rows above, and pin both in `test/conformance.test.ts`.

- `StatementRecordExists` is raised from the structured `AlreadyExists` error of kind `Record`.
- `StatementIndexConflict<Index>` is raised when the engine's message names a unique index the statement declares. Its `index` is typed as the union of those names.
- A write builder (`create`, `insert`, `insertRelation`, `update`, `upsert`, `relate`) over a descriptor declares that table's unique indexes, taken from `indexes`. A table with no unique index adds no `StatementIndexConflict` to the statement's error type. What `onDuplicate` and `INSERT IGNORE` declare follows what an engine test shows they can raise.
- `make` and `sequence(...).define` accept a declared list of index names for authored text.
- An index the statement does not declare, and a message that does not match the pinned pattern, stay `StatementRequestError`, as today.
- In a `transaction`, the error names the statement that declares the index, as `StatementThrown` does.
- Conformance tests cover a duplicate through `CREATE`, `INSERT`, `UPDATE`, `UPSERT` and `RELATE`, and an existing record through `CREATE` and `INSERT`, on both engine lanes.
- A type test shows `Effect.catchTag('StatementIndexConflict', (e) => e.index)` narrowed to the literal union.
- A test asserts that the message, `String(error)` and the JSON form of each new error contain no data value: neither the duplicated value nor a record key.
- The README's error table gains both rows, and the diagnostic snapshot is refreshed.

### L08. The file's comment and SQL in a part's doc comment

- The analyzer returns the comment that precedes a text's first statement.
- A generated part's doc comment holds that comment as prose, then the SurrealQL in a fenced block, then the file name.
- A text containing `*/`, a backtick or `${` still renders a module that compiles; a property test over generated texts proves it.
- Output stays deterministic. The goldens are regenerated, and that is the only difference in them.

### L04. Schema-derived types for authored files

Two steps, each closed by its own checks.

Projected fields:

- Inside one query whose target is exactly one static table, the analyzer records each bare field name the `SELECT` projects, and `*`.
- With `--schema`, or a scope's `declared` detail, a projected field that a `SCHEMAFULL` table does not declare fails generation with its file and line, for example ``selects `nmae` of `person`, which declares no such field``.
- Nothing is recorded for a function call, a path, an expression, an aliased expression, `VALUE`, `OMIT`, a graph step, a subquery in the projection, two targets, an open target or a schemaless table. One test per case asserts that.

Ready statements:

- A new `--store <module>` flag names the generated emitter index. Without it the output is byte for byte what it is today, which the existing goldens prove.
- With it, a file that is exactly one `SELECT` the analyzer reads completely is generated as a runnable statement instead of a `part`. The README states the recognised shape exactly: `*` or bare fields from one static `SCHEMAFULL` table, a `WHERE` of comparisons between bare fields and parameters joined by `AND`, an optional `ORDER BY` of bare fields, and an optional literal `LIMIT`.
- Its parameters take the codecs of the fields they are compared with, brands included, and its result is built from the descriptor's field codecs.
- Every other file is still a `part`.
- An engine test runs each generated ready statement through `run` on both engine lanes and decodes its rows. A type test uses one with no hand-written codec.

### L05. `statements --verify`

- A flag takes the schema as SurrealQL files, in the order they apply. It needs the optional peer `@surrealdb/node`; when the peer is missing the command fails with the install command.
- The command starts an in-process, in-memory engine, loads the schema, and sends each complete text once with no bindings.
- A parse error is a problem with the file, line and column the engine reports. A result count that differs from `slots` is a problem. Other errors a text meets with no bindings are not problems.
- It combines with `--check`, and writes nothing in that mode.
- The same check is exported as a function for a build that generates in process.
- `effect-surrealkit/analyze` stays host-neutral: a test asserts that its built module does not import `@surrealdb/node`.
- The README says that a verified text is executed on a discarded in-memory engine, and what that means for a text with effects outside the database.

### L09. JSON Schema of a statement's bindings

- A function returns the JSON Schema document of a statement's bindings, derived from their codecs through the JSON codec world and `Schema.toJsonSchemaDocument`.
- A binding whose codec has no JSON Schema is a typed failure that names the binding. It is never emitted as `{}`.
- A test validates sample inputs with `ajv` against the document, decodes them through the binding codecs, and checks that the encoded bindings equal what `run` sends.
- The README shows a statement exposed as a tool definition, with no new dependency.

### L10. A proven result key and total order

- A statement can carry two facts: `key`, the fields that identify a result row, and `ordered`, that its rows come in a total order.
- `select` sets `ordered` only when its `ORDER BY` ends with `id` or covers every column of one unique index, and sets `key` only when `id`, or every column of a unique index with no optional column, is projected. In every other case the fact is absent.
- `make` and `sequence(...).define` accept both as declarations.
- Type tests and unit tests cover each rule and its refusals. An engine test shows that an `ordered` statement returns rows with equal sort values in the same order on repeated runs.
- A paging helper is not part of this lane.

### L07. `.surql` imports through a content mapper

Experimental until TypeScript 7.1 is released. The protocol below is what reylo's source shows at `ba71851c` (`package.json:33-42`, `src/rpc.ts`, `src/mapper-server.ts`, `src/mapper-diagnostics.ts`, `src/register.ts`). It is not yet documented by TypeScript and has changed once, so pin the TypeScript build the fixture uses.

- The package declares a content mapper for `.surql` in `package.json`. The mapper is a process that speaks JSON-RPC 2.0 over stdio with `Content-Length` framing, and answers `initialize`, `openProject`, `transform` and `closeProject`. `transform` returns `{ extension: ".ts", text, mappings }`.
- The text returned for a file equals what `renderStatementModules` renders for it, byte for byte. A file's scope is its parent directory, as with the command.
- An analyzer error is reported inside the `.surql` file at the analyzer's line and column, and does not hide the type errors of other files.
- `node --import effect-surrealkit/register` loads a `.surql` import at run time, and `vite-plugin-surrealkit` gains an option that does the same in a build. Both produce the module the mapper described.
- A fixture project with its own pinned `typescript@7.1.0-dev` type-checks with `tsc --noEmit --runExternalCode`. A second fixture with a missing binding fails to compile at the import.
- The package's own type check stays on its current TypeScript. The mapper fixtures run as a separate CI job that is not a required check until TypeScript 7.1 is released.
- The README section is marked experimental and lists the requirements.

### L11. Rename proposals in `rollout plan`

- When a plan removes one field and adds one field on the same table whose definitions are identical apart from the name, `plan` records the pair in the manifest's `renames` and adds an expand-phase `run_sql` step that copies the old field's values into the new one, marked unconfirmed.
- `rollout lint` and `rollout start` refuse a manifest with an unconfirmed step, as they refuse a `revert_migration` step with an empty `using`. The author confirms the step or deletes it.
- The removal of the old field stays in the contract phase.
- When several removed and added fields could pair in more than one way, `plan` proposes nothing and lists the candidates in a warning.
- A manifest with no renames serialises exactly as before, so the checksum of every existing manifest is unchanged. A snapshot test proves it.
- Tests cover a detected rename, definitions that differ, the ambiguous case, and rows that keep their values through `rollout up` and `rollout up --complete` on the embedded engine.
- The `rollout_plan` MCP tool reports the proposal. The root README's "Migrating existing records" section describes it.

### L12. Property tests for rollouts

- `proptest` is added as a dev-dependency, with a generator of bounded schema pairs: tables, fields over a small set of kinds, indexes, and additions, removals and modifications between the two versions.
- On the embedded engine, for each pair: after `plan` and `up --complete` the catalog equals that of a fresh database synced to the second version; planning again produces nothing; a row's values in fields whose definition did not change are equal before and after; and for a plan the tool reports as reversible, `rollback` after `start` restores the first version's catalog and rows.
- A failure is shrunk, and its minimal case is committed as a fixture that runs as an ordinary test from then on.
- The number of cases is set by an environment variable. The default's measured run time is recorded in the test file's header.
